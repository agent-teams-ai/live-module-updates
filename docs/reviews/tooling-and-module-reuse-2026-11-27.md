## Feature-boundary decision

At base 77a3ecc, src contains 1,815 physical lines: 1,530 runtime and 285
testing-entry lines, across 19 files. Sixteen files belong to update-operation.
The 478-line coordinator already delegates invocation, generation ownership,
cleanup-report validation, operation observations and construction to bounded
private components and narrow ports.

Publication attempts, candidate custody, original receipts, predecessor work and
retirement are one cohesive operation. No independent consumer or second semantic
owner currently justifies separate sibling features. A split must not create
mutual mutable Attempt access, duplicated completion policy, a generic event bus
or a shared service bag.

Reconsider a sub-feature when a separately reasoned invocation/custody capability
has a curated internal contract, changes independently, and supports an acyclic
dependency graph without private state leakage. Reconsider a sibling feature
when another actual feature requires that independent capability. A separate
package additionally needs its own reuse, lifecycle or release boundary.
If the coordinator grows, first extract bounded private responsibilities while
preserving the one authoritative operation owner.

The whole-closure entry remains a composition adapter: it translates the already
constructed application's commands/results into LMU's entry and owns no business
state, authorization policy or second graph resolver. Moving it now did not
demonstrate a useful architectural guarantee.
