# Public runtime identity, semantic custody and safe drain

**2026-11-23 — executed bounded research. Not a production implementation, public lifecycle admission qualification, product adoption or complete updater E2E.** This follow-up refines the earlier [critical gaps](critical-evidence-gaps-2026-11-23.md), [cutover/custody](cutover-admission-and-state-custody-2026-11-23.md), and [closure/reclamation](closure-integrity-and-reclamation-2026-11-23.md) findings.

The research question is narrower than "can arbitrary JavaScript be safely hot-replaced?" It is whether the real, published Get Modular composition and resource APIs support the proposed custody boundaries, and which superficially plausible shortcuts fail. The answer matters before the first library operation and adapter are designed.

## Critical design refinements

### 1. Separate stable physical owners from stable semantic views

Published Assembly's slot-free input is suitable for explicit borrowing of a stable, externally owned capability. Its identity restrictions are meaningful; do not mislabel an arbitrary dependent module as an input to force reuse. The admitted operation needs the actual resolved code and dependency closure as well as any semantic view whose consistency the operation requires. P8 disproves "same provider reference implies one revision."

A stable transport, connection pool or state owner can legitimately serve many generations. An operation requiring coherent configuration can acquire one owner-supported immutable view/lease and reuse it after awaits. A deliberately latest-state query can use a different documented contract. Do not snapshot every mutable object, clone arbitrary state or turn Observation into a durable command ledger. Retain a product-owned state/read contract rather than introduce a parallel business-state authority.

### 2. Treat branded runtime identity as an explicit compatibility boundary

Get Modular Assembly and Resources authenticate entries/scopes through package-local identity. The [Assembly entry store](https://github.com/agent-teams-ai/get-modular/blob/850bac5fd02fa5697846cc8958ac447d5c2ee7bb/packages/assembly/src/features/construction/entry-store.ts), [Assembly run carrier checks](https://github.com/agent-teams-ai/get-modular/blob/850bac5fd02fa5697846cc8958ac447d5c2ee7bb/packages/assembly/src/features/construction/run.ts), and [Resources scope implementation](https://github.com/agent-teams-ai/get-modular/blob/850bac5fd02fa5697846cc8958ac447d5c2ee7bb/packages/resources/src/features/scope/scope.ts) at the inspected source head explain the observed separation. These source observations are paired with actual npm tests, not an assertion that the entire source tree equals a package archive.

Proposed ordinary trusted profile: retain the one compatible, actually resolved integration runtime instance for the host realm. Treat updating that foundation/runtime itself as a different operation with a separately qualified bridge, cohort or restart boundary. Reject an incompatible candidate before executable work where possible. Do not transfer branded objects between physical copies or across unsupported realms, and do not bypass identity checks with structural casts. Peer pins and loader sharing policy are evidence inputs; verify actual resolved instances rather than assume singleton configuration is a proof. Distinct loader/realm identities matter even when code bytes are equal.

This resembles the JVM's class identity (name plus defining loader) and .NET load-context type identity, not a reason to implement another module loader. Webpack offers actual share scopes, singleton and version constraints; already-used shared modules need not be replaced by offering a new remote. Vite's dedupe option has documented limits. These are mechanisms to use at their native boundaries, not an unconditional cross-bundler guarantee. References: [JVM SE25, creation/loading](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-5.html#jvms-5.3), [.NET AssemblyLoadContext](https://learn.microsoft.com/en-us/dotnet/core/dependency-loading/understanding-assemblyloadcontext), [webpack Module Federation](https://webpack.js.org/concepts/module-federation/), [webpack plugin sharing](https://webpack.js.org/plugins/module-federation-plugin/), [Vite resolve.dedupe](https://vite.dev/config/shared-options.html#resolve-dedupe), [Node ESM URL cache](https://nodejs.org/api/esm.html#urls). This campaign did not run those additional loaders.

### 3. Make ownership stronger than a successful return value

The Assembly invocation path calls the factory before validating its returned carrier. A pre-factory refusal (P5/P6) and a post-invocation unsupported carrier (P7) therefore cannot be collapsed into one safe failure class. A valid native resource acquisition followed by an exception before handoff (P10) is another distinct boundary.

Before candidate execution, establish a named attempt owner and a supported acquisition/effect contract. Keep physical acquisitions under that authority until registration, receipt or safe disposition. Acquire one handle, establish its cleanup ownership before performing fallible downstream initialization, and ensure partially failed acquisition is handled by its actual acquirer. Never infer cleanup from an empty created-entry list, absence of a returned value or generic completed status. Do not normalize an arbitrary foreign Promise with Promise.resolve and call it a proven adapter. An actual adapter needs an execution/return/late-work contract. Node's [vm contract](https://nodejs.org/api/vm.html) is not an isolation guarantee for hostile plugins.

### 4. Drain before prerequisite release; cancellation is not settlement

Resources is cooperative cleanup, not work admission or a call scheduler. The actual reverse close continues with other entries when one fails. P3's successful registered drain is not proof that a failed registered drain blocks release. P9 specifically rejects that assumption. If old work can still use a dependency, its owner must remain alive until an appropriate terminal barrier has been established independently; scope ordering alone cannot provide this guarantee. A retry may settle cleanup debt but cannot retroactively repair a failed old operation. Keep distinct evidence of useful work, drain, retention and actual release.

Reuse the existing product owner contract where it exists. Agent Runtime's [ADR-0024](https://github.com/agent-teams-ai/agent-runtime/tree/0ce60d7474159396132752a625c914ffa87c5049/docs) already requires host drain before resource-owner close; the prior [cutover/custody source audit](cutover-admission-and-state-custody-2026-11-23.md) links its exact source. Do not duplicate provider-session custody, process shutdown or resource registration in the library. Failure policy must keep ownership/retention and report debt or explicitly request a supported forced-stop profile; never turn a timeout into a release fact.

For async iterators, a cancel request, outstanding next, return, finalizer and physical handle closure can be separated. Preserve the lease through actual terminal settlement (including async finally) and ensure retained callbacks cannot initiate unauthorized new work after retirement. P12 establishes a bounded language/handle control; it does not establish every host's stream contract or liveness. A never-settling next/finalizer can keep the generation alive. Bound admitted work and retention; defer a new update rather than silently force termination.

### 5. Atomic admission must survive reentrancy

One synchronous JavaScript turn is not sufficient if code within it invokes synchronous callbacks before publication is internally complete. P11's actual abort callback observed a half-published route despite no external thread. Publish a complete coherent route/admission state before effectful notification, or use an existing qualified owner primitive that supplies the required atomic transition. No arbitrary user code or observers inside the partial state update; do not independently set selected/admitted then fire abort in between. The Resources acquisition gate protects that scope, not the host's canonical route. The earlier 25-schedule model and P11 are complementary, not a proof of an atomic public kernel.

### 6. Mature systems sharpen the boundary, not the dependency list

[Linux livepatch consistency](https://docs.kernel.org/livepatch/livepatch.html) uses per-task consistency and safe transition points; stalled tasks and forced transition have explicit consequences. [Erlang code server](https://www.erlang.org/doc/apps/kernel/code.html) distinguishes current/old code, soft purge refusal and destructive purge; finite code slots do not license killing a useful old process by default. [ArcSwap](https://docs.rs/arc-swap/latest/arc_swap/) illustrates retaining one consistent loaded value across related reads instead of repeatedly loading a moving reference. The earlier native Nginx experiment shows a different overlap/retirement mechanism in actual processes.

Take the semantic distinctions: compatible safe boundary, per-operation affinity, supported continuation, explicit finite retention, and separate forced retirement. Do not port any kernel, runtime, scheduler, registry or version-control protocol. Linux/OTP/ArcSwap are source comparisons only.

## First profile: narrowed conditional recommendation

No Q1–Q7 decision or actual product has been selected. A useful first qualification candidate remains a trusted cooperating TypeScript feature with one local route's immutable composed graph, explicitly borrowed stable owner(s), version-coherent operation input when required, one active plus bounded retained generation(s), and predeclared supported work/stream boundary. Keep ordinary TS first and Effect/remote/isolated adapters separately qualified. Consider refusing/defering the next update while an old generation cannot retire. A compatible restart/rollout is a truthful fallback, not a failure of the library to be "universal."

| Candidate scope | Fit now | Major remaining proof |
| --- | --- | --- |
| Trusted single-realm replacement with stable owner borrowing | Strong evidence to continue evaluation | Actual supported atomic select+admit/lease and product useful-operation cutover; P1–P12 do not implement it |
| Arbitrary dependent graph incremental reuse | Premature | Exact supported closure/substitution API, compatibility and ownership proof beyond slot-free inputs |
| Foundation/runtime upgrade or multiple realms | Separate profile | Actual compatible bridge, data/command semantics, old runtime retirement and physical identity |
| Arbitrary untrusted code, distributed writers, offline clients | Separate high-risk profiles | Real isolation, product receiver fencing and recovery, client asset lifetime and selected state contracts |

### Proposed acceptance gates for the next real consumer

1. **Before execution:** prove actual artifact/share/realm closure and supported public entry/carrier compatibility, reject foreign ownership before body; register a strong attempt owner.
2. **Publication:** qualify the existing public admission/custody mechanism (private candidate code is not a released dependency), including failed competing updates and actual reentrant callback, nested-call and stream retention. Do not implement a parallel private kernel to make a test pass.
3. **Useful operation:** use a small independent packed consumer with real A/B route; exercise an old admitted operation through await/next/finally while new work reaches B. Same stable owner, explicit semantic revision; test a late invalid acquisition, failed drain, and repeated update under a bounded retention budget.
4. **Recovery and state:** distinguish publish committed, useful adopted, drain settled, remaining cleanup, and uncertainty. Use the chosen consumer's canonical state/receiver authority and same-attempt recovery where durability is promised. Do not reimplement the host's database, effect ledger or session domain.
5. **Negative and physical controls:** preserve the prior outcome under retry, actual real-handle liveness/closure and rejection of incompatible runtime, unresolved drain or unsupported profile. A new admitted call must not inherit stale authority; no forced kill or unload claim without an actual qualified boundary.

S2's **public-package borrowing and cleanup boundary** is now materially evidenced. Its atomic invocation-admission, nested real routed consumer and independently packaged updater requirements are still open. S1/S3–S7 retain their proposed full scope; these native probes do not close them by analogy. Earlier schedule/SQLite/Nginx and Piral/Effect evidence retains its original counts and limits. No production API, library implementation, upstream pin, FMS/Docs admission, required-check policy, or release is changed.
